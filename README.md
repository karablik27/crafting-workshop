# Мастерская игровых предметов (ERC-1155 + Transparent Proxy)

Игроки превращают дерево и руду в мечи (`CraftingV1`). После запуска игра обновляется до
`CraftingV2`, в которой появляется разбор мечей; все предметы пользователей сохраняются.

```
src/
  CraftingV1.sol        — первая версия: issue + craft
  CraftingV2.sol        — вторая версия: наследует V1, добавляет salvage
test/
  CraftingBase.t.sol    — общая подготовка: развёртывание прокси и обновление через OZ Upgrades
  CraftingV1.t.sol      — правила V1: issue, craft, нехватка ресурсов, переводы и операторы
  CraftingV2.t.sol      — правила V2: salvage, откат при отказе получателя, fuzz-тест
  Upgrade.t.sol         — единый сценарий V1 → V2, проверка хранилища, права и инициализации
  mocks/PickyReceiver.sol — контракт-игрок, который может отклонять отдельные id
```

## Версии зависимостей

| Компонент | Версия |

Точные коммиты зафиксированы в `foundry.lock` и `.gitmodules`.

## Установка и запуск

```bash
# 1. Foundry (если ещё не установлен)
curl -L https://foundry.paradigm.xyz | bash
foundryup

# 2. Проект с зависимостями
git clone --recurse-submodules <url-репозитория>
cd crafting-workshop
# если клонировали без --recurse-submodules:
forge install   # или: git submodule update --init --recursive

# 3. Сборка и тесты
forge build
forge test --force          # --force обязателен для OZ Upgrades: валидация читает свежие артефакты
forge test --force -vvv     # с подробным выводом
```

При первом запуске `npx` скачает `@openzeppelin/upgrades-core` — нужен доступ в интернет.

В `foundry.toml` включены настройки, которые требует OpenZeppelin Upgrades:
`ffi = true`, `ast = true`, `build_info = true`, `extra_output = ["storageLayout"]`.

## Правила игры

| id | Предмет | Как появляется |
|---|---|---|
| 1 | Дерево | `issue` — только владелец игры |
| 2 | Руда | `issue` — только владелец игры, или `salvage` (V2) |
| 3 | Меч | только `craft` |

- **`issue(to, id, amount)`** — только владелец игры (`onlyOwner`). Разрешены лишь `id = 1` и `id = 2`
  (иначе `NotIssuable(id)`; меч через `issue` выпустить нельзя), `to != address(0)`
  (`ZeroAddress`), `amount > 0` (`ZeroAmount`).
- **`craft(n)`**, `n > 0` — сжигает у вызывающего `3n` дерева и `2n` руды, выдаёт ему `n` мечей,
  `totalCrafted += n`, событие `Crafted(player, n)`. При нехватке любого ресурса вся операция
  откатывается (`ERC1155InsufficientBalance`).
- **`salvage(n)`** (V2), `n > 0` — сжигает у вызывающего `n` мечей, выдаёт ему `n` руды,
  `totalSalvaged += n`, событие `Salvaged(player, n)`. Без мечей — откат.
- Обе операции работают только с предметами `msg.sender` и выдают результат ему же
  (оператор не может крафтить или разбирать чужие предметы).
- Порядок внутри операций — Checks-Effects-Interactions: сначала списание и счётчик, затем
  выпуск токена, который вызывает `onERC1155Received` у получателя-контракта. Если получатель
  отказывается, откатывается вся транзакция, включая списание и счётчик.
- `totalCrafted` разбором не уменьшается; обычные переводы ERC-1155 счётчики не меняют.
- Стандартные `safeTransferFrom`, `safeBatchTransferFrom`, `setApprovalForAll` работают как обычно.
  Публичных `mint`/`mintBatch` из шаблонов нет — новые предметы появляются только по правилам игры.

## Роли и обновление

Прокси разворачивается через `Upgrades.deployTransparentProxy("CraftingV1.sol", adminOwner,
abi.encodeCall(CraftingV1.initialize, (gameOwner)))`:

- `gameOwner` — владелец игры (`Ownable` внутри V1/V2), может только выдавать ресурсы;
- `adminOwner` — владелец `ProxyAdmin`, который создаёт `TransparentUpgradeableProxy`; только он
  может обновить реализацию. Это разные адреса — тесты проверяют, что ни посторонний, ни
  владелец игры обновить прокси не могут.

Защита инициализации:

- `initialize` помечен модификатором `initializer` и вызывается один раз при создании прокси;
  повторный вызов на прокси (и до, и после обновления) → `InvalidInitialization`.
- Конструктор реализации вызывает `_disableInitializers()`, поэтому напрямую инициализировать
  реализации V1 и V2 нельзя (V2 наследует этот конструктор).

## Почему данные сохраняются при обновлении

1. **Transparent Proxy хранит всё состояние у себя.** Реализация — только код, который
   выполняется через `delegatecall` в контексте прокси. Обновление меняет лишь адрес реализации
   в слоте EIP-1967; адрес прокси, балансы, разрешения операторов, владелец и счётчики остаются в
   хранилище прокси.
2. **Раскладка хранилища не меняется.** OpenZeppelin v5 хранит данные `ERC1155Upgradeable`,
   `OwnableUpgradeable` и `Initializable` в пространствах имён ERC-7201. Собственные данные игры
   устроены так же:
   - V1: `erc7201:crafting.storage.CraftingV1` → `{ totalCrafted }`;
   - V2: `erc7201:crafting.storage.CraftingV2` → `{ totalSalvaged }`.

   V2 наследует V1 и ничего не меняет в его структурах, а новый счётчик кладёт в отдельное
   пространство имён. Слоты не пересекаются, поэтому `totalSalvaged` после обновления равен нулю,
   а `totalCrafted` и всё остальное читаются из тех же слотов, что и раньше.
3. **Совместимость проверяется автоматически.** В `CraftingV2` стоит аннотация
   `@custom:oz-upgrades-from src/CraftingV1.sol:CraftingV1`, а исходник V1 сохранён в проекте.
   `Upgrades.upgradeProxy`, `Upgrades.prepareUpgrade` и `Upgrades.validateUpgrade` запускают
   OpenZeppelin Upgrades Core, который сравнивает раскладку хранилища V1 и V2 и ищет небезопасные
   конструкции (`selfdestruct`, `delegatecall`, неразрешённые конструкторы и т. п.). Проверка
   **не отключена** — `unsafeSkipAllChecks`/`unsafeSkipStorageCheck` не используются; при
   несовместимом изменении тест `test_ValidateUpgrade_V1ToV2` и само обновление падают.
4. **Новых данных инициализировать не нужно**, поэтому `upgradeProxy` вызывается без `data`, и
   повторной инициализации при обновлении не происходит.

Единый сценарий `test_FullScenario_V1ToV2` проверяет всё это: V1 → выпуск и крафт →
разрешение оператору → попытки чужого обновления → обновление владельцем `ProxyAdmin` →
сравнение адреса прокси, админа, владельца, балансов, разрешений и `totalCrafted` → перевод меча
оператором → разбор новым держателем → запрет повторной и прямой инициализации.

## Что покрыто тестами

- Успешный крафт и событие `Crafted`; глобальный счётчик; `craft(0)`; нехватка дерева, руды и
  обоих ресурсов; крафт только из своих предметов.
- Запрет чужого `issue` (в том числе владельцу `ProxyAdmin`), выпуска неизвестного id (0, 4),
  меча, нулевому адресу и нулевого количества; отсутствие `mint`/`mintBatch`.
- Получатель-контракт сначала принимает ресурсы, затем отклоняет меч при крафте — все балансы и
  `totalCrafted` прежние (в V1 и после обновления). Аналогично при отказе от руды в `salvage`.
- В момент получения меча ресурсы уже списаны, а `totalCrafted` уже увеличен (CEI).
- Разбор без мечей, при нехватке мечей, `salvage(0)`, разбор только своих мечей, событие `Salvaged`.
- Переводы не меняют счётчики.
- Fuzz-тест: для `1 ≤ n ≤ 1000` новый игрок получает `3n` дерева и `2n` руды, после `craft(n)` и
  `salvage(n)` у него остаётся только `n` руды, а `totalCrafted` и `totalSalvaged` выросли на `n`.

Все обращения к игре в тестах идут по адресу прокси; адреса реализаций используются только для
проверки, что их нельзя инициализировать напрямую.
